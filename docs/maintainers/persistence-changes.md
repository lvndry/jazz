# Changing persisted formats

Jazz writes files that a later or an earlier build reads: conversation logs, goal and run records, job batches, reminders, the spend ledger, plugin consent, config. A build that reads a shape it does not understand loses data or acts on a stale decision. This page is the rule that prevents that, and the gate that enforces the part of it a machine can check.

## The rule

A change to a persisted shape does one of two things.

1. **It breaks older readers.** Bump the store's format version, write an adjacent-version migration (version N-1 to N, never a jump over versions), and add a regression test that reads a fixture of the previous version. Bumping makes an older build refuse the file instead of rewriting a format it does not understand; see [`state-file.ts`](../../packages/core/src/utils/state-file.ts) and `CONVERSATION_LOG_VERSION` in [`conversation-log.ts`](../../packages/adapters/src/history/conversation-log.ts).
2. **Older readers still work** (a new optional field that readers ignore, a widened union that old writers never produce). Leave the version and record that in the store's changelog.

Existing migrations are not retrofitted; the rule applies to the next change.

## The gate

`bun run verify:persistence` runs in the CI lint job and in the unit tests. It compares each store in [`persistence-registry.ts`](../../scripts/persistence-registry.ts) with its checked-in snapshot.

- **Registry.** One entry per store: name, location under the Jazz home, where its version lives (an existing constant, or `unversioned` with the reason), and the declarations that define its shape. A store with no declarations is listed as a gap.
- **Snapshot.** `persistence/snapshots/<store>.json` holds the version and the printed text of each declaration, with comments and `export` removed, and a hash of that text. It is generated by `bun run gen:persistence`; do not edit it by hand.
- **Changelog.** `persistence/changelog/<store>.json` holds reviewed acknowledgements, each naming the new shape hash, the version, a one-sentence description, and `readersOfOldFormatStillWork`.

The check fails when:

- a store has no snapshot (run `bun run gen:persistence`);
- a shape changed at the same version with no acknowledgement for the new hash;
- a versioned store acknowledges a change that breaks readers without bumping its version;
- a version went down, or a snapshot was edited by hand;
- a snapshot is stale after a legitimate change (regenerate it).

`bun run gen:persistence` writes only what the gate allows, so regenerating never turns a violation into a pass. The failure message names the changed declarations and the exact entry to add. Reviewers read the changelog entry and the snapshot diff together.

## Adding a store

Add it to the registry with its version constant (or `unversioned`), run `bun run gen:persistence`, and commit the snapshot and the empty changelog. Prefer a Zod schema or an exported type as the declaration, so the shape has one definition the reader validates against.

## What the gate cannot see

The shape is the text of the listed declarations. It does not follow references: a change to a type that a declaration only names (a message part, a presentation entry) is invisible unless that type is listed too. It does not read hand-written validators, so a stricter parser over the same type passes. It compares shapes and versions, not migrations: it cannot tell that a migration or a fixture test exists. Stores listed as gaps in the registry have only their version tracked.

Review those cases by hand: when a diff touches how a file is read or written, ask what a build one version older, and one version newer, does with it.
